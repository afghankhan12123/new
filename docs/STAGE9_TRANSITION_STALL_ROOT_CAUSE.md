# Transition stall investigation and repair

## Proven from production source

1. Both compositor adapters chose a nearest secondary frame without constraining it to the active layer's visible interval. A last transparent pad before a transition could qualify at its first primary timestamp; a first transparent pad after it could be nearer than the final real picture. The primary video is intentionally hidden during that transition. Therefore this algorithm could submit padding instead of mandatory transition video. `SecondaryFrameSelector` now selects only `[layerStart, layerEnd)` in preview and export.
2. A secondary queue containing only its last picture behind the primary timestamp waited for a future picture unless the ENTIRE sequence had ended. Transition lanes are reusable sequences of pads and handle intervals, so sequence EOS is the wrong condition for an individual handle. The preview renderer already knew some decoded period endpoints, but did not pass that knowledge to compositor selection. It now marks both valid-last-buffer and postroll completion; the graph waits for that period's final registered GL output, then publishes a generation-scoped interval watermark. This permits the final real picture to cover only its confirmed interval; it does not terminally end the reusable VFP/lane.
3. A retained padding lease preceding a newly required interval was kept even when it could never be valid there. Both adapters now release that invalid prefix, allowing upstream pool/stream handoff to progress. Hidden streams discard obsolete prefix pictures and do not gate output merely because they are not registered. Every currently required input still must register and supply a valid picture; ended-but-visible ordinary overlays no longer disappear silently.
4. The controller's watchdog covered startup/explicit seeks, then stopped after output arrived. A subsequent natural-playback stall could remain Loading indefinitely. `PlaybackOutputWatchdog` checks submitted-picture progress while playback is requested, including buffering. After four seconds without new output, the existing single-replacement recovery policy applies. One replacement picture does not renew the playback incident budget: output must advance through half a second, or a second stall exposes Retry with input/queue diagnostics. The editable project survives.

## Ownership path examined

`CompositionBuilder` → `ProjectRenderPlan` / resolved source windows → outgoing/incoming padded sequences → `PreviewSequenceRenderersFactory` packet/source timestamp mapping → `InputVideoSink` stream/reset bookkeeping → `CancellablePreviewVideoGraph` shared GL executor → compositor input IDs / interval selection → shared `Stage9CompositorProgram` → composition overlay/background passes → submitted-output timestamps. Export retains its independent DefaultVideoCompositor/Transformer execution and shares the interval selector and render semantics.

The two reusable transition lanes, canonical source-time evaluator, nonoverlapping windows, atomic `TransitionHandlePlanner.Apply`, actual source trimming and complete inverse timeline snapshot remain. Source-handle adjustment leaves music, voiceover, text, stickers and PiP at their authored project positions; this anchoring rule is shown during explicit review. Exact visible removal amounts account for each clip's speed. No source media is rewritten.

## Not established

The recording has no decoder/GL logs or per-input queue trace. It does NOT establish which of the above defects caused the owner's particular 23.5s stall, or rule out another device-specific failure. These are concrete algorithm/lifecycle corrections, not a claimed runtime root-cause reproduction. They require device testing across all thirteen types, multiple joins and backward seeks. Hardware pixel checks must confirm that padding exclusion, watermark delivery and stream handoff behave as intended. Build success cannot prove shader pixels, codec availability or AV synchronization.
